1. 结论摘要

先说结论：Navi 的工程质量、部署链路与自动化程度明显强于 NavDeck；但在「中文用户的检索体验」和「首页的信息密度」两件事上落后。 NavDeck 值得学的不是功能数量，而是它把目标人群的真实痛点直接做进核心功能这一取舍方式。

判断内容说明
我们领先 服务发现、本地图床库、零依赖架构、测试与发布链路 这四项是真正的护城河，改进过程中不能牺牲
我们落后 拼音搜索、全局搜索面板、卡片级内外网策略、图标离线可用、首页状态板 前四项成本低、感知强，列为 P0 / P1
需要正视 图标依赖公共 CDN；备份不含图片 前者影响离线/局域网可用性（NAS 场景的核心），后者影响换机迁移
不必跟 强绑定 Lucky、引入前端框架、为状态板引入重依赖 详见第 5 章，各有明确理由
最值得借鉴的一条设计思想：NavDeck 的「同步只标记失效、不直接删除，支持一键恢复」。 这是自动化功能的安全阀——自动生成/同步类功能一旦做错，用户的损失是不可逆的。 Navi 的「服务发现」目前是「生成候选 → 用户勾选 → 加入」，已经比较安全，但缺少来源标记与失效追踪， 这块值得补上（见 P1-7）。

2. 对标对象：NavDeck 的设计理念与实现

2.1 它解决什么问题

NavDeck 定位是部署在自有 NAS 上的导航起始页：把 qBittorrent、Jellyfin、Alist 等自托管服务做成卡片，分类归档、拖拽排序、点击直达。 它的目标人群非常明确——「服务装了 5 个以上的 NAS 玩家」。

2.2 五个核心功能

功能做法解决的痛点
内外网自动切换 每张卡片同时填内网 + 外网地址；策略设「自动」后探测哪个可达就跳哪个；也可固定只走内网/外网 在家走内网 IP、出门走公网域名，不必维护两套链接
拼音全局搜索 Ctrl + K 唤起；匹配名称子串 + 全拼 + 拼音首字母缩写（找 Jellyfin 敲 jlc） 卡片多到一屏放不下时，比翻卡片快得多
Docker 监控 + Widget 栏 挂载 docker.sock 后首页显示容器在线/停止/总数、CPU/内存/磁盘 IO 水位，30 秒自动刷新；另有倒数日、正数日小组件 首页从「书签集合」升维成「状态板」
Lucky 反代规则同步 填 Lucky 后台地址 + OpenToken，一键把反代规则变成卡片：前端域名→外网地址，后端地址→内网地址 手上有几十条反代规则时，不用手工建卡
细节体验 内置 275+ 自托管服务图标、自动抓 favicon、本地上传；浏览器地址栏链接直接拖进页面建卡；明暗主题、自定义壁纸、一键导出 zip 备份 降低建卡和维护的摩擦

2.3 技术实现要点

  • 分发：官方镜像走 GHCR，README 首推不克隆源码、不本地构建；一条 docker compose -f docker-compose.prod.yml up -d 起服务。
  • 配置：.env 三件套 —— AUTH_SECRET（openssl rand -base64 32 生成）、AUTH_USERNAME、AUTH_PASSWORD，并明确警告「别用默认的 admin/changeme，登录前就改掉」。
  • 权限：需要 Docker 状态就挂 /var/run/docker.sock；Linux 上遇到容器内权限问题按 README 设 DOCKER_GID 解决。
  • 降级设计（关键）：docker.sock 挂载失败时只是 Widget 降级显示，其他功能不受影响。
  • 持久化：所有数据在 data 目录，换 NAS 时「整个目录 + 备份 zip」一起带走。

2.4 运营模式

维度做法
协议与节奏MIT 开源；迭代很勤（发文时 v0.4.2 刚发布）
文档官方手册 + README；README 首推镜像方式，把部署门槛压到最低
拉新靠中文自媒体文章（本文即其一）承载「场景故事 + 功能讲解 + 部署步骤」，文末导流关注
预期管理明确写出「什么人值得上」与「什么人不太适合」，并主动承认「项目还年轻、迭代快，正式用起来前多导出几份备份」
值得注意的运营手法：它不掩饰短板。主动说清「不合适谁」和「有什么风险」， 反而是可信度来源。这一点我们完全可以照做——Navi 的文档目前全是「怎么做」，缺「适合谁」。

3.3 三处需要正视的短板（本轮新发现）

短板一：图标依赖公共 CDN，离线/局域网会「白图」。 resolveIcon() 把图标解析成 api.iconify.design 或 cdn.jsdelivr.net 的外链。 这意味着：纯内网 / 断网环境下，所有图标都加载不出来——而 NAS 导航站恰恰常在这种环境里用。 更麻烦的是，这个依赖还让测试出现「假失败」（CDN 抖动被当成 JS 错误，本项目已用桩测试绕过，但根因未解）。 NavDeck 的选择是内置 275+ 图标，不依赖外网。
短板二：备份不含图片，换机迁移会丢图床库。 buildBackup() 只序列化 config，图片全在 data/uploads/ 里没有进包。 而 NavDeck 是「整个 data 目录加备份 zip 带走」。用户若靠备份迁移，会静默丢失所有上传的图标。
短板三：内置图标/指纹库偏小。 SERVICE_PRESETS 实测 33 条（NavDeck 是 275+）。 虽然可以走在线图标库补，但离线时可选范围很窄；且没有「自动抓网站 favicon」这条兜底路径， 用户填了 URL 却没填图标时，只能靠 Dashboard Icons 的 slug 猜测。

5. 判断：值得借鉴什么、不必跟什么

5.1 值得借鉴的五条

#借鉴点为什么对我们有价值
1拼音检索我们的用户是中文用户，卡片名混合中英（「网易云音乐」「Portainer」）。子串匹配对中文输入法用户很不友好——想找「网易云音乐」得打全名，或打「163」碰运气
2卡片级内外网策略 + 可达性探测我们已有 lanUrl 字段和全局开关，只差最后一公里。目前的 hostname 启发式在常见场景会判错
3首页状态板我们已经有零依赖的 Docker API 客户端，做这件事的边际成本极低，但产品定位能从「书签页」升到「NAS 控制台」
4同步只标记失效、不删除、可恢复这是自动化的安全阀。我们的服务发现虽然已经「先候选后确认」，但仍缺少「来源追踪 + 失效管理」
5内置图标、离线可用直接解决短板一。NAS 导航站经常在内网/断网环境用，图标不该依赖外网

5.2 不必跟的三条（附理由）

不必跟理由
强绑定 Lucky 同步 把核心功能绑死在某个第三方工具上，会把受众收窄到「用 Lucky 的人」。我们的服务发现覆盖面更广： 只要是 Docker 容器或本机监听端口就能识别，不要求用户装特定反代。
→ 可以补充通用导入（粘贴 JSON / NPM 导出），但不做单一工具强绑定。
引入前端框架 / 构建链 我们最大的差异优势是「零依赖 + 零构建」：与 CPU 架构天然解耦、镜像极小、435 项断言直接跑在源码上。 换框架会摧毁现有测试资产，且对一个单页导航站来说是负收益。
→ 要拆的是模块，不是换技术栈（见 8.1）。
为状态板引入重依赖 NavDeck 的资源水位可以用现成的系统库。我们必须自己读 /proc——但这不难， 且沿用已有的降级模式即可（读不到就显示「不可用」，不影响其他功能）。不为了一个 Widget 破坏零依赖。

6. 改进方案 · P0（立即做）

P0 的判据：成本可控、用户当天就能感知、且不触碰架构红线。

P0-1　拼音搜索（全拼 + 首字母缩写）P0

现状itemMatches() 只做 indexOf 子串匹配，无拼音能力。

方案新增 public/js/pinyin.js —— 纯数据表，不引入任何 npm 依赖：

  • 内置常用汉字（约 3,500 字，一级 + 二级常用字）→ 拼音映射，紧凑 JSON 格式约 25–35 KB。
  • 把拼音表做成独立静态资源懒加载：首屏不加载，用户首次输入字母/中文时才 fetch，避免拖慢首页。
  • 只对卡片标题做索引（标题短、且是用户真正会打的内容），生成两个派生字段缓存在内存：py（全拼串，如 wangyiyunyinyue）与 pyi（首字母串，如 wyyy）。
  • 匹配优先级（分数从高到低）：标题精确子串 → 拼音首字母 → 拼音全拼 → 描述 → URL。

验收输入 jlc 命中 Jellyfin；输入 wyyy 与 wangyiyun 均命中网易云音乐； 输入 qb 命中 qBittorrent；拼音表加载失败时自动退回纯子串匹配（不得因此报错或空白）。

效果中文用户的「找卡片」动作从「回忆全名」变成「打几个字母」。

P0-2　全局搜索面板（Ctrl+K）+ 搜索引擎跳转P0

现状只有 / 聚焦输入框 + 过滤网格；无结果浮层、无键盘导航、无引擎跳转。

方案

  • 新增搜索浮层：Ctrl+K（macOS 兼容 ⌘K）唤起，/ 保留为兼容快捷键。
  • 键盘交互：↑ ↓ 移动选中项、Enter 新标签打开、Esc 关闭；鼠标悬停同步高亮。
  • 结果分组显示：分组名作为小节标题（沿用现有分组结构，无需新数据模型）。
  • 高亮匹配片段（标题中的命中字符加粗/着色），让用户一眼知道为什么命中。
  • 引擎跳转：新增配置 site.searchEngines: [{name, url}]（url 里用 %s 占位），并提供 site.defaultEngine。 面板底部显示「用 某引擎 搜索 "关键词"」作为最后一项；回车即跳转。

验收Ctrl+K 能唤起浮层；↑↓ 能改选中项；Enter 打开正确站点； 输入 如何学习 vim 回车走默认引擎；旧配置（无 searchEngines）下该行不显示且不报错。

效果搜索从「过滤器」升级为「命令面板」，这是 NavDeck 最直接的体验优势。

P0-3　卡片级内外网策略 + 可达性探测P0

现状全局一个开关，卡片无法单独例外；判定靠访问主机名启发式，在「用公网域名访问但身处内网」等场景会判错。

方案

  • 数据模型：item.netMode = "auto" | "lan" | "wan"，默认 auto（缺省时行为与现状兼容，老配置无需迁移）。
  • 探测策略不照抄 NavDeck 的「点击时探测」（每次点击都等探测会明显变卡），改为： 页面加载后异步并发探测一次，对存在 lanUrl 的卡片发起 fetch(lanUrl, { mode: "no-cors", signal: AbortSignal.timeout(1200) })， 把「内网是否可达」缓存在内存并设 TTL（建议 5 分钟）。
  • 点击时同步决策（不等网络）：可达 → 用 lanUrl；不可达 → 用 url；探测尚未返回 → 立即按启发式兜底跳转，不阻塞用户。
  • 三级回退：netMode 显式设定 → 探测结果 → hostname 启发式。全局开关降级为「强制覆盖」（对齐 NavDeck 的「固定只走内网/外网」）。
  • 卡片上给出轻量标识（如内网可用时显示小圆点），让用户知道当前会走哪个地址。
必须诚实说明的浏览器限制：如果导航站本身通过 HTTPS 访问， 浏览器会以 mixed content 为由阻止对 http://内网IP 的探测请求，探测会恒失败并全部回退到外网地址。 我们的实际部署是局域网 HTTP 访问，不受影响；但文档必须写明这条边界，否则用户用 HTTPS 反代时会遇到「自动切换不生效」且找不到原因。

验收内网可达时点卡片走内网地址；离开内网后自动改走外网；探测超时不阻塞跳转； HTTPS 场景下的回退行为符合预期且在文档中有说明。

效果补齐 NavDeck 最受好评的功能，且体验比它更好（不阻塞点击）。

P0-4　备份纳入图片（zip 导出 / 导入）P0

现状buildBackup() 只含 config；图片在 data/uploads/ 里不进包 → 换机迁移静默丢图标。

方案

  • 新增 GET /api/backup?format=zip：打包 config.json + uploads/** + manifest.json。 ZIP 由内置 zlib 手写（local file header + central directory），不引入依赖。
  • manifest.json 记录每个文件的 sha256 与字节数，恢复时逐项校验——把现有「校验和」这一优势延续到 zip 上。
  • POST /api/backup/restore 扩展为同时接受现有 JSON 与 zip（按内容嗅探，不靠扩展名）， 旧备份文件继续可用。
  • 恢复前先备份当前 uploads/ 到临时目录，失败可回滚——避免「恢复了一半」的中间态。

验收导出 zip → 在全新环境导入 → 卡片、分组、图床图片全部还原； 旧版 JSON 备份仍可正常导入；篡改 zip 内任一文件后导入被拒绝并给出具体文件名。

效果「换 NAS 整个带走」这句话对我们才真正成立。

7. 改进方案 · P1（提升定位）

P1-5　首页 Widget 状态板P1

现状discovery.js 已有零依赖 Docker Engine API 客户端，但只用于生成卡片，不展示状态。

方案

  • 新增 GET /api/status，一次返回：容器统计（运行中 / 已停止 / 总数，复用 /containers/json?all=true） + 资源水位（CPU 由 os.cpus() 差值计算；内存读 /proc/meminfo；磁盘读 /proc/diskstats）。
  • 前端在时钟下方新增 Widget 栏，30 秒轮询，页面隐藏时（document.hidden）暂停轮询省电。
  • 降级是一等公民：Docker 不可用 → 该 Widget 显示「Docker 不可用」，其余功能完全不受影响； 非 Linux 环境（/proc 不存在）→ 资源 Widget 显示「不支持」，不报错、不抛异常。
  • 倒数日 / 纪念日：纯前端，数据存 site.widgets[]（{type:"countdown"|"countup", title, date}）， 与 P0 系列无耦合，可独立上线。

验收挂载 docker.sock 时显示真实容器数；不挂载时页面无 JS 错误、 其余功能全正常；轮询在标签页隐藏时停止。

效果首页从「书签集合」变成「NAS 状态板」——这是产品定位的实质性提升。

P1-6　内置图标扩容（33 → 200+）与 favicon 兜底P1

现状SERVICE_PRESETS 33 条；图标实际走公共 CDN；无 favicon 抓取。 离线/内网环境下图标全部加载不出来（NAS 场景的常见工况）。

方案

  • 把「服务指纹库」与「图标别名表」合并为一份可维护数据文件 public/icons/presets.json，扩充到 200+ 常见自托管服务，含 name / aliases / ports / icon。
  • 内置图标资源本地化：把高频图标随镜像一起打包（SVG 体积小）， 解析顺序改为 本地内置 → 图床库 → 在线 CDN。这直接解决短板一。
  • 补 favicon 兜底链：卡片填了 url 但无 icon 时，依次尝试 本地内置库 → /favicon.ico（同源代理，绕开跨域）→ 首字母占位图。
  • 新增 GET /api/favicon?url= 服务端代理抓取并缓存到 data/uploads/favicons/， 避免浏览器跨域限制、同时让图标「抓一次就离线可用」。

验收断网状态下，200+ 内置服务图标全部正常显示； 新建卡片只填 URL 时能自动拿到 favicon 并落盘；CDN 不可达时不产生控制台 JS 错误。

效果既补齐离线可用性，也从根因上消除「CDN 抖动导致测试假失败」这一历史问题。

P1-7　发现/导入的来源追踪与失效管理P1

现状服务发现生成的卡片加入后即成为普通卡片，无法区分「手工建的」与「自动发现的」，也没有失效追踪。

方案（直接借鉴 NavDeck「只标记、不删除、可恢复」的语义）

  • 卡片新增可选字段 source: {type:"discover"|"manual"|"import", id, syncedAt}。
  • 重新扫描时做全量 diff：源侧消失的卡片只标记 stale: true，不删除， 前端以弱化样式提示「来源已失效」。
  • 提供两个显式动作：一键恢复（清掉 stale）与 清理失效项（需二次确认）。
  • stale 卡片在导出/备份中照常保留，避免用户在不知情时丢数据。

验收停掉一个容器后重新扫描，对应卡片仍在且标记为失效；恢复容器后可一键复原； 清理动作有二次确认且不影响手工卡片。

效果把「自动生成卡片」这个我们已经领先的功能，补上它缺失的安全阀。

8. 改进方案 · P2（生态与运营）

8.1 架构专项：拆分单文件，但不引入构建

现状app.js 73 KB、server.js 43 KB、discovery.js 34 KB，均为单文件。

判断按当前规模尚可维护，但P0/P1 会再增加 3–4 个模块（拼音、搜索面板、Widget、favicon）， 继续堆进 app.js 会失控。建议在动手做 P0 之前先拆，否则后面拆更贵。

方案

  • 前端按功能拆成 js/app.js（主控）+ js/pinyin.js + js/search.js + js/widgets.js + js/discover.js + js/library.js， 用原生 ES Module（type="module"）组织——零构建、零依赖的红线不破。
  • 注意：现有资源版本号机制（?v= 由服务端按 mtime 自动生成）需要覆盖到新增的 JS 文件， 确保缓存策略继续自动生效。
  • 服务端同理，可拆 routes/ 目录；server.js 只保留路由分发与启动。
  • 拆分的验收前提：435 项断言在拆分后仍全部通过——这是安全网，必须先跑通再拆。
顺序很重要：先让测试全绿 → 拆分 → 再跑测试 → 确认数字不变 → 才动新功能。 项目已有的「反向验证」文化（故意破坏护栏看测试是否报警）正是为这种重构准备的。

11. 风险与取舍

风险说明对策
拼音词典体积 全量拼音库可达数百 KB，会拖慢首屏 只收常用 3,500 字、独立资源懒加载、只索引标题； 加载失败自动退回子串匹配
HTTPS 下探测失效 mixed content 会阻止对 HTTP 内网地址的探测 文档明确写出；三级回退保证功能不坏； 提供手动固定「仅内网/仅外网」的兜底开关
手写 ZIP 的兼容性 ZIP 格式细节多（编码、UTF-8 标志位、中央目录偏移） 只支持 store / deflate 两种方法；文件名限定 ASCII（uploads/ 内已是我们生成的 hash 名）； 用三个真实解压工具交叉验证
拆分重构引入回归 73KB 单文件搬家容易改坏行为 先全绿 → 拆 → 再全绿，断言数必须一致；重构与功能改动分开提交
图标素材的版权 内置图标随镜像分发涉及许可 优先采用 permissive 许可的图标集（Simple Icons 等）；保留来源与许可说明文件
状态板的额外攻击面 docker.sock 等价宿主机 root 权限 保持默认不挂载、:ro 只读、文档保留现有安全警告； 状态板只读不写（不提供重启容器等操作）
与 NavDeck 的定位差异 我们会越来越像它，可能失去「极简」特色 所有 Widget 与增强默认关闭或可隐藏，保持「打开即用」的极简默认态

11.1 取舍原则

三条判断标准，用于未来遇到类似取舍时复用：

  1. 是否服务于「中文 NAS 用户」？是 → 优先。这是 NavDeck 成功的根本原因，也是我们该守的定位。
  2. 能否离线可用？不能 → 必须有降级路径。NAS 场景断网/内网是常态，不是异常。
  3. 是否破坏零依赖与测试资产？是 → 换方案。这两个是我们的护城河，不是可选项。
